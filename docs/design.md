# EasyImporter 设计方案

- 生成方式：/office-hours，2026-11-10
- 状态：DRAFT
- 类型：公司内部项目
- 相关文档：[架构设计](architecture.md) · [接口设计](api.md) · [部署方案](deployment.md) · [原始方案](archive/README-original.md)

## 1. 问题

业务数据以 Excel 形式产生，进库靠开发或运维用 Navicat、DBeaver、达梦管理工具的导入向导手工完成。这些工具只认单行表头的扁平表格。遇到合并单元格的多级表头（如“1月份 / 销售额”），必须先手工把表格整理成扁平结构，再逐列对字段。每换一种表格就重做一遍，既没有复用，也没有导入记录。

EasyImporter 把“整理表格、对字段、导入”变成一次配置、反复使用的模板，让业务人员自己完成导入。

## 2. 现状与替代对象

| 环节 | 现在的做法 | EasyImporter 的做法 |
|---|---|---|
| 复合表头 | 手工拆合并单元格、拼列名 | 自动识别表头树 |
| 宽表转长表 | 手工复制粘贴成多行 | 模板里配置“拆行”规则 |
| 字段对应 | 每次在向导里逐列选择 | 模板保存映射，下次自动套用 |
| 数据校验 | 导入报错后再查 | 提交前逐行校验，在网格里直接改 |
| 追溯 | 无 | 留存原始文件、任务日志、操作人 |

## 3. 用户与角色

- **管理员**（开发 / 运维）：登记数据源，管理用户和工作区，创建和维护模板。
- **导入员**（业务人员）：在所属工作区里选模板、上传文件、修正数据、提交导入、查看结果。看不到数据库连接信息。

## 4. 约束

- 规模：单文件 1 千到 5 万行（拆行后），同时 1 到 5 人导入。
- 目标库：PostgreSQL、MySQL、达梦 DM8。
- 部署：x86 联网、x86 离线内网、信创（国产 OS + ARM）三种环境都要支持。
- 界面：中英文，明 / 暗 / 跟随系统主题。

## 5. 已确认的前提

1. **定位**：替代数据库客户端的手工导入。第一版核心是复合表头识别，以及“宽表直映”和“长表拆行”两种映射。不做通用 ETL，不做跨表关联，不做多 sheet 合并。
2. **安全**：只有管理员能登记数据源，连接密码在服务端加密存储。前端只传 `datasource_id`。模板绑定具体目标表，导入员无法写其他表。
3. **执行**：任务持久化在元数据库，由独立 worker 进程领取执行。用数据库表做队列，第一版不引入 Redis。
4. **一致性**：一个导入任务要么全部生效，要么全部不生效。“按范围替换”用同一事务内的 `DELETE … WHERE 范围` 加 `INSERT`，不用 `TRUNCATE`。
5. **先校验再写入**：提交前对全部行做类型、必填、长度等校验，生成逐行错误，用户在网格里改完再提交。
6. **自动匹配**：以“归一化后精确匹配 + 同义词表 + 模板历史映射”为主，编辑距离只在同分时排序。
7. **部署**：amd64 / arm64 双架构镜像，提供离线包。元数据库默认 PostgreSQL，可换成达梦或 MySQL。

## 6. 方案对比

| | A 前端解析直传 | B 后端解析 + 暂存表 | **C 前端解析 + 后端复核（选定）** |
|---|---|---|---|
| Excel 解析 | 浏览器 | 后端 | 浏览器 |
| 校验 | 只在前端 | 只在后端 | 规则由后端生成，前端提示，后端复核 |
| 原始文件 | 不留存 | 留存 | 留存 |
| 网格编辑 | 本地，无延迟 | 分页回写，有延迟 | 本地，无延迟 |
| 工作量 | M | L | M+ |
| 主要风险 | 绕过前端可写入脏数据 | 暂存表和分页编辑带来额外复杂度 | 规则格式只支持单列规则 |

选 C 的原因：数据量是万行级，B 的暂存表现在用不上；导入员是业务人员，必须由后端最终把关，A 做不到。以后数据量超过十万行时，可以从 C 演进到 B：规则和文件留存已经在后端，只需把解析搬到后端。

## 7. 核心流程

1. **管理员建模板**：选数据源和目标表 → 上传一份样例 Excel → 系统识别表头树 → 自动匹配字段，管理员调整 → 配置拆行规则、写入策略、业务键 → 保存。
2. **导入员导入**：选模板 → 上传 Excel → 浏览器在 Web Worker 里解析，按模板转换成规范行，并按下发的规则校验 → 网格展示，错误单元格标红 → 用户修改直到没有错误 → 提交。
3. **后端处理**：API 保存原始文件和规范行，创建任务（状态 `QUEUED`）后立即返回 → worker 领取任务，用同一份规则复核全部行 → 复核不通过：任务 `FAILED`，返回逐行错误，不写库 → 复核通过：在一个事务里按策略写入目标表 → `SUCCEEDED`。
4. **查看结果**：导入记录列表，展示每个任务的进度、日志、写入行数和错误明细，可以下载错误报告（带错误说明列的 Excel）。

## 8. 复合表头识别

**输入**：sheet 名、表头起始行 `headerStartRow`、表头行数 `headerRowCount`。模板保存这三项；上传样例时系统给出建议值，管理员可以改。

**算法**：

1. 读取 `worksheet.model.merges` 得到合并区域，只保留与表头行相交的区域。原方案里的 `worksheet.getImages()` 读的是图片，与合并单元格无关，不能用。
2. 对表头区域的每个单元格，若属于某个合并区域，取左上角主单元格（`cell.master`）的值。
3. 对每一列，自上而下收集各行的值，得到路径，例如 `["1月份", "销售额"]`。
4. 清理路径：去掉首尾空白和换行，全角转半角；连续两层值相同的只保留一层（纵向合并造成）；空值层跳过。单层表头的路径就是 `["流水号"]`。
5. 同一路径出现多次时，按出现顺序加后缀 `#2`、`#3`，并在界面上提示。
6. 构造成树返回给界面展示，同时保留每个叶子的列号。

**样例上传和正式导入的对应关系**：正式导入时，按**路径**而不是列号找列。列顺序变了不影响；模板里的必需路径缺失时，报 `TEMPLATE_HEADER_MISMATCH` 并列出缺少的路径；多出来的列忽略并提示。

**单元格取值**：

| 单元格类型（ExcelJS） | 取值 |
|---|---|
| 公式 `{ formula, result }` | 取 `result`；没有缓存结果时报 `CELL_FORMULA_NO_RESULT` |
| 富文本 `{ richText: [...] }` | 拼接各段 `text` |
| 超链接 `{ text, hyperlink }` | 取 `text` |
| `Date` | ExcelJS 按 UTC 返回，按 UTC 取年月日时分秒，不做时区换算；工作簿 `date1904` 为真时已由 ExcelJS 处理 |
| 错误值 `{ error: '#N/A' }` | 视为该单元格校验失败 |
| 数字、字符串、布尔 | 原样 |

- 数据区从表头下一行开始。连续 10 行所有映射列都为空时视为数据结束（这样可以跳过带格式的尾部空行）；中间的空行跳过，不报错。
- 隐藏的行和列照常读取，界面上提示“包含隐藏行 N 行”。

**性能**：浏览器版 ExcelJS 的 `xlsx.load` 会一次解析整个工作簿，流式读取只在 Node 端可用，所以“只读前 N 行”省不了解析时间，只是减少表头处理的工作量。20 MB 的文件可能占用数百 MB 内存，解析放在 Web Worker 里，避免页面卡死。合并区域很多时解析会明显变慢（见 [exceljs#2689](https://github.com/exceljs/exceljs/issues/2689)）。上传大小上限和内存占用要在 M0 用真实文件实测后再定（见待定问题 8）。

## 9. 映射模型

模板的映射由两部分组成：**普通列映射**和**拆行组**。

```json
{
  "columns": [
    { "excel_path": ["水单号"], "db_column": "serial_no" },
    { "excel_path": ["公司"],   "db_column": "company" }
  ],
  "unpivot": {
    "dimension_column": "month",
    "groups": [
      { "dimension_value": "2026-01", "match_prefix": ["1月份"] },
      { "dimension_value": "2026-02", "match_prefix": ["2月份"] }
    ],
    "measures": [
      { "excel_leaf": "销售额", "db_column": "sales_amount" },
      { "excel_leaf": "利润",   "db_column": "profit_margin" }
    ]
  },
  "constants": [
    { "db_column": "source", "value": "excel" }
  ]
}
```

- **宽表直映**：不配置 `unpivot`，每个路径映射到一个库字段，一行 Excel 产生一行。
- **长表拆行**：`groups` 的每一项产生一行。该行包含所有普通列，`dimension_column` 取 `dimension_value`，各度量列取 `match_prefix + excel_leaf` 对应的单元格。12 个月份就是一行 Excel 拆成 12 行。
- 一个模板最多一个拆行组。某一组的度量列全部为空时，不产生这一行（可在模板里关闭此行为）。
- `constants` 用于写入 Excel 里没有的固定值；第一版支持字面量，以及 `${import_id}`、`${imported_at}`、`${operator}` 三个变量。
- 界面上，管理员可以在表头树上选中“1月份”到“12月份”这一层，一键生成 `groups`，`dimension_value` 默认取表头文字，可批量改写。

## 10. 自动匹配

原方案用编辑距离比较“1月份_销售额”和“January Sales Amount”，两者字符几乎不重合，得分没有意义。改为按以下顺序打分，取最高分：

| 优先级 | 规则 | 分数 |
|---|---|---|
| 1 | 该模板（或同一目标表的其他模板）的历史映射里出现过同一路径 | 100 |
| 2 | 叶子名归一化后与字段注释完全相等 | 90 |
| 3 | 叶子名归一化后与字段名完全相等 | 85 |
| 4 | 通过同义词表命中（如“水单号 = 流水号 = serial_no”） | 80 |
| 5 | 字段注释包含叶子名，或叶子名包含字段注释 | 60 |
| 6 | 编辑距离相似度 ≥ 0.6 | 相似度 × 50 |

- 归一化：去空白和标点，全角转半角，英文转小写，去掉“(元)”“（%）”这类单位后缀。
- 拆行模式下，用叶子名（“销售额”）匹配，不用完整路径。
- 一个库字段只能被一个路径占用；冲突时高分者优先，其余标为“待确认”。
- 低于 60 分不自动连线，只在下拉框里排在前面。
- 同义词表按工作区维护，存成**同义词组**：一组里的词互相等价，例如 `{水单号, 流水号, serial_no}`。匹配时，叶子名和字段名（或注释）落在同一组即命中。管理员每次手动修正后，系统会提示“加入同义词表”。

## 11. 校验规则

后端根据目标表元数据和模板设置生成规则，以 JSON 下发给前端；前端执行同一份规则做实时提示，worker 复核时再执行一遍。

```json
{ "db_column": "sales_amount", "type": "decimal", "precision": 18, "scale": 2,
  "required": false, "default": "0.00", "max_length": null, "enum": null, "pattern": null }
```

- 类型：`string`、`integer`、`decimal`、`boolean`、`date`、`datetime`。由库字段类型推导，管理员可以收紧（加必填、枚举、正则），不能放宽。
- 转换：数字去千分位；“是 / 否 / Y / N / 1 / 0”转布尔；日期接受 Excel 序列号和 `yyyy-MM-dd`、`yyyy/M/d` 等常见格式，统一转为 ISO 字符串；百分比按模板设置转为小数。
- 空值：库字段非空且没有默认值时为必填；可在模板里给某列设默认值。原方案日志中“金额为空按 0.00 处理”属于这里的默认值，需要显式配置，不会自动发生。**默认值由 worker 填充**并记录 `DEFAULT_APPLIED` 日志；前端只在单元格里以灰字显示将要使用的默认值，不写入提交的数据。
- 第一版只支持单列规则，另加一条内置的整批规则：**业务键在本次数据内不能重复**（`UPSERT`、`REPLACE_SCOPE`，以及设置了业务键的 `APPEND` 都检查）。重复的行全部标红，前端和 worker 都执行。其他跨列规则（如“结束日期 ≥ 开始日期”）列入后续版本。
- **提交的数据由后端重新约束**：worker 只接受模板里映射到的列，其他键一律丢弃；`constants` 的值由 worker 填充，覆盖前端提交的同名字段，防止导入员伪造。
- 前端执行规则的实现和后端 Pydantic 校验共用一组测试样例（`fixtures/rules/*.json`），保证两边结论一致。

## 12. 写入策略

| 策略 | 行为 | 前提 |
|---|---|---|
| `APPEND` | 只插入。设置了业务键时，写入前先查询已存在的键，有冲突就整批失败并列出全部冲突行；没设业务键时，遇到数据库约束错误整批失败，只能报出数据库返回的第一条冲突 | 无（业务键可选） |
| `UPSERT` | 业务键存在则更新映射到的列，不存在则插入 | 模板指定业务键，且目标表上有对应的唯一索引 |
| `REPLACE_SCOPE` | 先删除指定范围的数据，再插入 | 模板指定范围列，如 `month`、`company`，范围列必填 |

- 原方案的 `TRUNCATE_INSERT` 改名为 `REPLACE_SCOPE`。`TRUNCATE` 会清空整张表，而需求是“清空当前月份 / 工作区的数据”；而且 `TRUNCATE` 在 MySQL 和达梦里会隐式提交，无法放进事务回滚。
- 删除范围取本次数据里**范围列组合**的去重值，按元组删除，不能每列分别用 `IN`。例如本次数据是 (A公司, 2026-01) 和 (B公司, 2026-02)，执行 `DELETE FROM t WHERE (company='A公司' AND month='2026-01') OR (company='B公司' AND month='2026-02')`；如果写成两个 `IN`，会把 (A公司, 2026-02) 也删掉。只有一个范围列时退化为 `IN`。组合超过 500 个时分多条语句，仍在同一事务里执行。
- 范围列在规则里强制为必填，因为 `IN (NULL)` 什么也匹配不到，旧数据删不掉，新数据会叠加上去。
- 提交前，确认页调用预估接口，显示“将删除约 N 行”，导入员确认后才能提交。worker 执行时按实际数据重新计算范围，不使用预估结果。
- UPSERT 语法按库区分：PostgreSQL 用 `INSERT … ON CONFLICT (…) DO UPDATE`，MySQL 用 `INSERT … ON DUPLICATE KEY UPDATE`，达梦用 `MERGE INTO`。由写入层按方言生成，参数化执行。
- MySQL 的 `ON DUPLICATE KEY UPDATE` 会被**任意**唯一索引触发，不只是业务键。所以 MySQL 上，如果目标表还有其他唯一索引、且它的列在映射里，保存模板时报 `UPSERT_AMBIGUOUS_UNIQUE_KEY`，拒绝保存。
- 写入行数统计：`inserted` 和 `updated` 在 MySQL（更新一行计为 2 行受影响）和达梦 `MERGE` 上拿不到精确值。这两个库只保证 `processed`（处理行数）准确，`inserted / updated` 为尽力估算，界面上标注“约”。
- MySQL 目标表必须是 InnoDB。元数据探查时检查表引擎，MyISAM 等不支持事务的引擎在保存模板时拒绝（`TABLE_ENGINE_NOT_TRANSACTIONAL`），否则无法保证失败后回滚。
- 整个任务在一个事务里执行，按 1000 行一批发送语句；任何一批失败都回滚整个事务。5 万行以内的单事务在三种库上都可以接受，需要在 POC 里实测达梦的耗时和锁表情况（见待定问题 3）。
- 写入层只操作模板绑定的那一张表，表名和列名来自元数据探查结果并做白名单校验，不拼接用户输入。

## 13. 安全

- **数据源凭据**：用 AES-GCM 加密后存进元数据库。主密钥来自环境变量 `EI_SECRET_KEY`，启动时缺失则拒绝启动；用 HKDF 从主密钥派生两把子密钥，一把用于加密，一把用于签名，互不复用。接口只返回脱敏信息（主机、库名、用户名），永远不返回密码。
- **最小权限**：文档建议管理员给每个数据源单独建数据库账号，只授予目标表的 `SELECT / INSERT / UPDATE / DELETE`。
- **网络访问**：数据源的主机可以由管理员任意填写，等于让服务端去连任意地址。用配置项 `EI_DATASOURCE_ALLOWED_HOSTS`（主机或网段白名单）限制，默认为空表示不限制，生产环境应当配置。
- **登录**：本地账号，密码用 argon2 哈希。会话存在服务端的 `sessions` 表里，Cookie 只带随机会话 id，设置 `HttpOnly`、`SameSite=Lax`，启用 HTTPS 时加 `Secure`。退出登录、停用用户、修改密码都会删除该用户的会话，立即生效。会话 8 小时无操作即过期。写操作校验 CSRF token。登录失败 5 次锁定 15 分钟。
- **提交数据**：解压后的规范行大小有上限（默认 200 MB，超出直接拒绝），防止 gzip 炸弹。行数必须与 `meta.row_count` 一致。
- **权限**：导入员只能访问自己所属工作区的模板和任务；所有数据源和模板管理接口仅管理员可用。
- **上传**：只接受 `.xlsx`，文件大小上限默认 20 MB（可配置），按扩展名和文件头校验。文件按任务 id 存储，文件名不参与路径拼接。
- **日志**：日志和错误信息不记录连接串、密码，也不记录整行业务数据；逐行错误只记录行号、列名和原因。

## 14. 不在第一版范围内

多 sheet 一次导入、跨列和跨表校验、导出模板、定时导入、SSO / LDAP、`.xls` 和 CSV、十万行以上的大文件、对外开放 API。

## 15. 待定问题

1. **真实样例**：需要 5 份当前手工导入的真实 Excel 和目标表 DDL，用来验证表头识别和拆行规则能不能覆盖。这是开工前最重要的输入。
2. **业务键**：UPSERT 依赖目标表上已有唯一索引。如果业务表没有，是要求 DBA 加索引，还是由 EasyImporter 先查后写（性能差，且有并发问题）？建议前者。
3. **达梦单事务上限**：5 万行单事务在达梦上的耗时、回滚段占用、锁表影响，需要 POC 实测。超出可接受范围时，`APPEND` 改为“写入临时表再一次性 `INSERT … SELECT`”。
4. **同一张表的并发导入**：两个任务同时写同一目标表、同一范围时，第一版按“同一目标表同时只运行一个任务”串行处理，是否满足需求？
5. **元数据库用达梦时的任务领取**：任务领取依赖 `SELECT … FOR UPDATE SKIP LOCKED`。PostgreSQL 和 MySQL 8 支持，达梦需要验证；不支持时改为“乐观更新状态字段”的方式领取。
6. **数据网格选型**：shadcn-vue 不含数据网格。候选是 TanStack Table + TanStack Virtual（自己实现编辑、粘贴）和 AG Grid Community（功能全，体积大）。需要用 5 万行做一次 POC 再定。
7. **原始文件保留期**：默认保留 90 天后清理，是否符合公司的数据留存要求？文件清理后，该任务不能再“重新执行”。
8. **浏览器内存**：浏览器版 ExcelJS 一次加载整个工作簿，需要在 M0 用 20 MB 真实文件实测内存和耗时，据此定上传上限。如果撑不住，考虑换用 SheetJS（同样整体加载，但内存更省），或者提前演进到后端解析。
9. **元数据库用达梦时的迁移**：Alembic 需要为达梦注册方言实现，否则会报 `KeyError`；还要验证 dmSQLAlchemy 对 JSON 列的支持，以及迁移锁在三种库上分别怎么实现。不行的话，JSON 字段在达梦上改存 `CLOB` 文本。

## 16. 成功标准

- 5 份真实样例中至少 4 份无需手工整理表格即可导入。
- 一份已建好模板的表格，业务人员从上传到导入完成不超过 5 分钟。
- 5 万行（拆行后）从提交到写入完成，PostgreSQL / MySQL 不超过 1 分钟，达梦不超过 3 分钟。
- 校验失败或写入失败时，目标表数据不发生任何变化（有自动化测试覆盖三种库、三种策略）。
- 前端规则和后端规则在共享样例上的结论 100% 一致。
